# The set code is the key — a tcgdex code↔name map, and what it does not touch

**Date:** 2026-09-05 · **Mode:** READ-ONLY against prod (no writes, no dispatches, no merges)
**Follows:** `unknown-setkey-2026-09-05.md` (#1796), which sized the population this PR acts on.

## The finding in one paragraph

The unknown-setKey census measured ~500,161 sales that need **vocabulary** rather than a checklist,
and named the Pokémon share as promo and set-code spellings. Those rows are not a vocabulary we lack —
they are a vocabulary we **already own and could not reach**. `POKEMON_SET_ALIASES` has held the full
English set list since 2026-08-16 (1,497 aliases over 214 sets, generated from tcgdex), and #1801 made
it reachable from a title. But it is keyed by set **NAME**, and these titles never spell the name; they
spell the **CODE**. This PR adds the code side of the same table, gated inside the Pokémon branch, and
adds no vocabulary to the sports normalizer at all.

| pokemontcg.io | **non-commercial only** | **REFUSED** | `dev.pokemontcg.io/terms` — the free tier is non-commercial and HobbyIQ is a commercial product. (It also returned HTTP 502 when probed on 2026-09-05, but the licence is the disqualifier, not the outage.) |
| Bulbapedia | **CC BY-NC-SA 2.5** | **REFUSED** | The NC clause forbids commercial reuse. Corroboration is not a lesser use — a fact copied from an NC source is still copied. |

**tcgdex is Pokémon-only.** Its `/v2/en/series` returns 21 series and every one is Pokémon
(`base`, `gym`, `neo`, `ex`, `dp`, `xy`, `sm`, `swsh`, `sv`, `me`, `tcgp`, …). It cannot serve One
Piece, Yu-Gi-Oh, Lorcana or Magic, which is part of why those verticals get a measurement here and not
a vocabulary.

## What the map is

Generated by `backend/scripts/fetchPokemonSetCodes.cjs` into
`backend/src/services/catalog/pokemonSetCodes.ts`. **378 codes**, in three parts:

| part | codes | what it is |
|---|---:|---|
| `POKEMON_EN_SET_CODES` | 205 | English set ids — the catalog's own setKey spelling |
| `POKEMON_PROMO_SET_CODES` | 13 | Black Star / promo ids — **the census's largest Pokémon rows** |
| `POKEMON_JA_SET_CODES` | 160 | Japanese-only ids |
| `AMBIGUOUS_MARKET_CODES` | 24 | codes both markets use for **different products** — refused, see below |

The value of each record is the set **name**, kept as documentation so a reader can tell `me02` from
`me02-5` without a second lookup. The **key** is the canonical setKey.

| `2025 Pokemon Japanese M2a-Mega Dream ex` | 1,142 | `Unknown` | **`m2a`** |

### The promo spelling is not the promo code, and that is a real finding

tcgdex names the set `swshp`. **Sellers never write that.** The census's rows say
`swsh black star promo` and `sm black star promo` — the **era prefix** plus the words. So the promo
branch reads the era prefix, and only when the title also carries "promo" or "black star" (an era
prefix alone is a whole series, not a set). The era→code mapping is *derived from the promo table*
(a promo code ending in `p`, minus the `p`), not authored, so a new era's promo set is covered the
day tcgdex publishes it.

## Where it is gated, and why that is the whole design

The resolver lives in `parseTitleIdentity.service.ts`, inside the **Pokémon branch of
`inferSetKeyFromTitle`** — behind the non-sports guard and behind a test that the title names Pokémon.
It is the same place #1801 put the name lane, for the same reason.

**No TCG vocabulary is added to `normalizeSetKey`.** The census warned, with measurements, that that
function already collapses unrelated TCG products onto sports keys —
`one piece op12-legacy` → `panini-legacy`, `uno elite` → `donruss-elite`, `cgc pristine mega gengar` →
`topps-pristine`. Adding codes there would pool One Piece sales into Panini pools. Nothing in this PR
touches it.

### Three rules contain the risk, because a code can look like a card number

1. **Segment-boundary matching, never a substring** — so `sv08-5` inside a serial cannot claim a set.
2. **A code of ≤3 characters is refused unless the title says "promo" / "black star."** 146 of the 378
   codes are that short and several are ordinary tokens in a sports title: `sp` is "Sample", `rc` is
   "Radiant Collection", `lc` is "Legendary Collection", `g1` is "Generations", `a1` is "Genetic Apex".
   A bare `RC` in "Charizard RC 25" is a card number far more often than a set, and a wrong key that
   passes the slug guard is worse than no key (CF-UNKNOWN-IS-ALSO-A-GUESS).
3. **The 24 ambiguous market codes are refused outright from a bare code.**

### The ambiguity that decided the design

24 ids exist in **both** markets naming **different products**:

```
sm1   EN "Sun & Moon"       vs JA "サン＆ムーン" (Collection Sun)
sm10  EN "Unbroken Bonds"   vs JA "ダブルブレイズ" (Double Blaze)
sv10  EN "Destined Rivals"  vs JA "ロケット団の栄光" (Glory of Team Rocket)
xy2   EN "Flashfire"        vs JA "ワイルドブレイズ" (Wild Blaze)
neo1  EN "Neo Genesis"      vs JA "金、銀、新世界へ..."
…20 more
```

Different prints, different markets, different prices. A bare `sm1` in a title says nothing about which
card the sale is, so the resolver **declines** rather than pool one market into the other. They are
absent from the Japanese table by construction, which is the same rule
CF-THE-JAPANESE-CODE-IS-THE-KEY states for `swsh12` — a Japanese reading must never drag an English
product onto a Japanese key, nor the reverse.

**tcgdex independently corroborates every ruled Japanese key.** `sv2a` = ポケモンカード151,
`sv8a` = テラスタルフェスex, `s12a` = VSTARユニバース, `s10a` = ダークファンタズマ,
`s8b` = VMAXクライマックス — exactly the codes Drew ruled on 2026-09-01 and 2026-09-04, arrived at from
an independent source.

## The tests, and which of them are load-bearing

16 tests in `backend/tests/pokemonSetCodeIsTheKey.test.ts`. The happy path is the least interesting
part:

- **A data-driven fixed-point pin over all 378 codes** — every emittable key must survive
  `normalizeSetKey` unchanged, and none may normalize onto a `panini-` / `topps-` / `bowman-` /
  `donruss-` / `upper-deck-` key. This is deliberately *data-driven rather than a list*: a new tcgdex
  set that collides with a sports pattern fails the day it is generated, which a hand-written list
  would not catch.
- **A mutation check that a SPORTS title never resolves through the code map**, asserted on titles
  carrying `sp`, `rc`, `lc`, `g1`, `a1` — the exact tokens the map contains.
- **A sports title that *also* says "promo" / "black star" is still sports** — the combination most
  likely to misfire, since the promo branch reads era prefixes. `2023 Panini Prizm Black Star Promo
  Wembanyama` → `panini-prizm`, not a Pokémon promo set.
- **The #1801 boundary re-pinned in both directions** — a Japanese title still never reaches the
  English NAME vocabulary (`151` is `sv03-5` in English and `sv2a` in Japanese), and an English title
  never reaches the Japanese code table.
- **Mutation checks that each lane is reachable** — they fail if the resolver call is deleted, which is
  the regression that would silently restore the defect.

All 75 pre-existing Pokémon tests and 312 normalizer/setKey tests pass unchanged.

## One Piece / Yu-Gi-Oh / Lorcana / Magic — measured, not touched

Drew's ask is explicit that these get **no vocabulary** in this pass, and
CF-POKEMON-TCG-EXPANSION-PARKED parks the vertical behind the sport→vertical refactor. What they get
here is a measurement, so the refactor can be costed against real money rather than a hunch, and a
source scan so the acquisition question is answered before it is asked.

### Source candidates, checked

| game | candidate | reachable | licence | note |
|---|---|---|---|---|
| Magic | **Scryfall** (`api.scryfall.com`) | yes — 1,049 sets, code + name | "free with attribution"; commercial terms are **not explicit** | `MTG_SET_ALIASES` already exists in the repo. **Needs a licence ruling before it is a source.** |
| Yu-Gi-Oh | **YGOPRODeck** (`db.ygoprodeck.com`) | yes — 1,035 sets, `set_code` + `set_name` | community API, terms not stated on the endpoint | `YUGIOH_SET_ALIASES` already exists and the code comments cite a 97.8% match rate. **Needs a licence ruling.** |
| Lorcana | `api.lorcana-api.com` / `lorcanajson.org` | yes — sets with `Set_ID`, name, card count, release date | not stated | no aliases exist yet |
| One Piece | `optcgapi.com` | yes — sets with `set_id` (`OP-01`) + `set_name` | not stated | no aliases exist yet |

**None of these is used in this PR.** Each is reachable and each would need the same licence check
tcgdex passed and pokemontcg.io failed. That check is a ruling, not a scrape.

### The volume census, and why this report does not quote a number

A read-only per-vertical census (rows, dollars, 90-day velocity, unknown-key share) was written and
run against prod on 2026-09-05: `COUNT` and `SUM` per `c.sport` over `sold_comps`, plus the
`CONTAINS(c.cardId, ":unknown:")` share of each.

**It did not return within the session's budget**, and that is itself the finding worth recording:
a per-vertical aggregate over a 20M-row container is a cross-partition scan measured at **>50 minutes
without completing**, which is the same shape #1796 hit when its product-level query
(`WHERE c.setKey=@sk AND c.cardYear=@y`) failed to return in four minutes. The first
`GROUP BY c.sport` formulation was worse still and had to be abandoned; the per-vertical rewrite is
the one that ran.

So **no volume number is quoted here rather than an estimated one**, per the census's own rule that a
number presented as measured had better be measured. What the vertical-refactor decision needs is a
count of rows and dollars per TCG vertical, and getting it wants either a cheaper access path
(the pre-aggregated container, or `sport` as a partition-aligned filter) or a job with a longer budget
than an interactive session. That is a small, well-defined follow-on, and the script is committed
ready to run:

```bash
COSMOS_CONNECTION_STRING="$(az webapp config appsettings list --name HobbyIQ3 \
  --resource-group rg-hobbyiq-dev \
  --query "[?name=='COSMOS_CONNECTION_STRING'].value" -o tsv)" \
node backend/scripts/census-tcg-verticals.cjs --json=/tmp/tcg-verticals.json
```

What IS established without it: **tcgdex cannot serve these four games** (all 21 of its series are
Pokémon), and each candidate source above needs a licence ruling first. Those two facts are the
gating questions for the vertical refactor, and neither depends on the row count.

## What this PR does NOT do

- It does **not** write to Cosmos. No lane is started, no fleet is dispatched, no row is repaired.
  The rows this map now derives become fleet fixes on the next `scope=improve` pass, under the
  existing canary gate, with no new code.
- It does **not** add a key to `normalizeSetKey`, and it does not touch the collapse defect
  (`one piece op12-legacy` → `panini-legacy`). That remains the HALT the census named.
- It does **not** unpark the TCG vertical. The sport→vertical refactor is still the blocker for One
  Piece / Yu-Gi-Oh / Lorcana / Magic.
- It does **not** claim a checklist. Recognising a product is not the same as holding its parallels —
  a code this map resolves still lands not-checklist-backed until real checklist rows exist for it,
  and the fleet will not write those rows until they do.

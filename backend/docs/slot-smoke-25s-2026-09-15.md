# Slot smoke: withheld-with-a-price, and the 25 s on BCP-69

Run 34989816447, sha `e25c7824`. Swap correctly refused; prod stayed on `31f18295`.

## Defect 1 — a withheld verdict carried $875

**Not a partial walk, not a cache, not `resolvedMarketValue`.** The withheld
object is correct when it is created and is **overwritten after the fact**.

`compiq.routes.ts` `/api/compiq/price`:

```
:3177   const result = await withPriceDeadline(query, () => cacheWrap(...))
          -> on expiry returns priceDeadlineWithheld():
             fairMarketValue: null, marketValue: null, pricingTier: "no-basis",
             fmvReason: "ladder-timeout", verdict: "Withheld — ..."

:4513   const { overlayResolverRescue } = await import(
          "../services/compiq/resolverFallbackHelper.js");
:4518   await overlayResolverRescue(result, {...});      // MUTATES result

:4532   res.json(result);
```

`resolverFallbackHelper.ts:116-137`:

```ts
const hasFmv =
  (typeof response.fairMarketValueLive === "number" && response.fairMarketValueLive > 0) ||
  (typeof response.marketValue === "number" && response.marketValue > 0);
if (hasFmv) return response;              // <- the ONLY guard

const fallback = await tryResolverFallback(query);
if (!fallback) return response;
response.fairMarketValueLive = fallback.fairMarketValue;   // $875
response.marketValue        = fallback.fairMarketValue;    // $875
response.approximate        = true;
```

The rescue asks one question — *"is there a price?"* — and a withheld verdict
answers **no** for the same reason a CH catalog-miss does. It cannot tell
"the engine declined" from "the engine found nothing", so it rescues the
refusal. The verdict string survives untouched because the rescue never reads
it, which is why the response self-contradicts: `no-basis`, mechanism `none`,
`verdict: Withheld …`, **`FMV $875`**.

This predates the deadline: any withheld path reaching `res.json` on this route
has always been rescuable. #2170 simply made it reachable often enough to be
seen.

Smoke output, case 4:

```
▶ 4 (parallel-floor → withheld):  2026 Bowman Chrome Owen Carey Black BCP-69...
  tier:       no-basis
  FMV:        $875
```

**Fix:** the rescue must refuse a response that has already stated a reason,
and the withheld shape must zero tier/mechanism/confidence rather than only the
price fields.

## Defect 2 — the 25 s, and the warm question

### The warm step DID call /api/health/warm — the hypothesis is wrong

From the run log:

```
15:41:31.949  slot healthy after 1 tries
15:41:31.949  Warming ...
15:41:32.030  {"ok":true,"totalMs":17,"steps":[
                {"checklist-parallel-corpus":9},{"bare-colour-alias-corpus":0},
                {"card-query-parser":8},{"valuation-module-graph":0}]}
```

So the workflow is **not** at fault, and no workflow diff is proposed.

### What the numbers actually say

`totalMs: 17` is the tell. A genuinely cold process pays ~2,555 ms here
(measured for #2196: bare-colour 1,256 ms, module graph 699 ms, corpus 329 ms,
parser 270 ms). **17 ms means everything was already built** — i.e. the warm
call reached a process that had been running for some time, not the one just
deployed.

The timeline supports that:

```
15:39:54.044   slot build-info builtAt (the package we deployed)
15:40:33.108   "Package deployment using OneDeploy initiated"
15:41:24.593   OneDeploy returns
15:41:31.949   /api/health -> 200 on the FIRST try, 0.09 s into the step
15:41:32.030   /api/health/warm -> totalMs 17  (already warm)
15:41:35.750   smoke starts
15:42:21.461   case 4 answers after 25,321 ms
```

Health answered 200 **immediately**, before App Service had recycled the worker
onto the new package. The warm step therefore warmed the **outgoing** process,
and the smoke then hit the **incoming** cold one. `slot healthy after 1 tries`
is the symptom: a poll that is satisfied by the process being replaced tells
you nothing about the process that will serve.

### Cosmos / 60 s timeouts on the slot

**Cannot be confirmed from telemetry — the slot emitted none.** Querying
15:30–16:15Z returns 15 request rows and **zero from
`hobbyiq3-staging-aebjecgpd7bvbshq…`**; every row is production or
`hobbyiq3-worker`. The slot has `APPLICATIONINSIGHTS_CONNECTION_STRING`
(shared, verified) and `HIQ_SLOT_ROLE` (sticky, verified), so the absence is
not a missing key.

Two candidate explanations, neither yet distinguished:
1. the slot process was still starting and had not flushed a first export when
   the smoke ran and the swap was refused shortly after;
2. `cloud_RoleName` is `HobbyIQ3` for both, so slot rows are only separable by
   `url` host — and there are none with the slot host.

So the honest statement is: **no evidence of 60 s `card_catalog` timeouts on
the slot, and no evidence against**. The 25 s is fully explained by a cold
process without invoking them, and 25,321 ms is suspiciously close to
`PRICE_REQUEST_DEADLINE_MS = 25,000` — i.e. the request hit the route deadline,
which is exactly what a cold ladder walk would do.

### Recommended fix (not workflow)

Make the health poll prove it is talking to the **new** build before warming:
compare `/api/health`'s `build.shaShort` against the sha being deployed, and
keep polling until they match. Then warm, then smoke. That is a workflow change
after all — but a different one from the proposed diff, and it fixes the real
sequencing bug rather than a warm call that already happens.

Prod is unaffected: it does its own `warmStart()` at boot and had 2.9 s Ohtani.
